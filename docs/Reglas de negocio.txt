1#USUARIO
    .) Nombre unico y no repetible entre usuarios
    .) Al borrar un usuario que sea DM se le da baja lógica a todas las Campañas de las que sea dueño 
    .) Cuando se borra un Usuario se lo quita de todas las Campañas donde es jugador
    .) se borra el usuario --> entonces se borran todos los personajes que haya creado el usuario

2#CAMPAÑA
    .) Creada por un solo Usuario
    .) Estado = ["planificada" / "activa" / "pausada" / "finalizada"]
    .) Transiciones de estado válidas : planificada → activa → pausada ⇄ activa → finalizada
    .) Al borrar una campaña, se le da baja lógica.
    .) Al borrar una campaña se le da baja a todos los eventos y personajes no jugables que tenga asociados
    .) Los objetos asociados a una campaña que es borrada solo se les dará baja si no tienen un PersonajeCampana asociado
    .) MASTER --> El master no debería poder agregarse a sí mismo como jugador de su propia campaña
    .) si el estado de la campaña es "finalizada" no se pueden agregar jugadores ni eventos ni modificar a "PersonajeCampana"

3#Evento
  .) Un evento no puede reciclarse para otra campaña
  .) "Comenzar campaña y activar evento" --> solo el MASTER puede hacerlo
  .) Un evento puede tener un estado (pendiente, en curso, finalizado)

4#Imagen
  .) un evento  puede tener una imagen asociada
  .) un personaje  puede tener una imagen asociada
  .) un usuario  puede tener una imagen asociada
  .) un objeto puede tener una imagen asociada

5#Personaje
  .) Los personajes son creados por usuarios.
  .)  Un personaje puede tener un tipo (jugable, no jugable)
  .) tipo = jugable -->
        .) Se crea una "plantilla" con el personaje a nivel 1, luego, 
           se genera una instancia para cada campaña en la que participe dicho personaje
           donde se guardarán todos los cambios.
        .) Los personajes jugables son aquellos que se podrán ver desde la pestaña de 'mis personajes'
        .) Luego de seleccionar uno, se podrá seleccionar la plantilla, o cualquiera de sus instancias.   
        .) un personaje jugable puede ser agregado a una campaña por su creador 
        .) un personaje jugable solo puede ser eliminado por su creador 
        .) Un personaje jugable puede estar en varias campañas
  .) tipo = no jugable -->
        .) "estadoAgresion" = ["hostil" | "neutral" | "amistoso"]  (es un ejemplo)
  .) Un personaje solo puede ser modificado o creado por el Usuario que lo creó 
  .) Las instancias de PersonajeCampana también pueden ser modificadas por el DM de la campaña a la que pertenezcan
  .) El DM puede desvincular un personaje de su campaña.
  .) No se puede cambiar el tipo de personaje

6#PersonajeCampana (instancia dentro de una campaña — el "estado en vivo")
  .) Es de tipo @unique --> esta instanicia de personaje solo puede estar en una campaña 
  .) vidaActual no debe ser mayor a vidaMaxima, ni negativo
      .) si vidaActual = 0 --> el personaje está "muerto" y no puede participar en eventos ---Ver dee crear un estado "muerto" para PersonajeCampana---
  .) manaActual no debe ser mayor a manaMax, ni negativo
  .) Si se elimina un personajeCampana de una Campaña que ha sido eliminada, se realiza un chequeo
     en lo objetos, rasgos y acciones específicos de dicha campaña, en caso de que hayan quedado 'huérfanos'
     (no estén asociados a ningún otro personajeCampana) serán eliminados.

7#Objetos
  .) valor --> solo puede ser positivo
  .) Un objeto puede estar en el kit inicial de un Personaje y/o en el inventario de un PersonajeCampana
  .) Un objeto puede ser general, o específico de una campaña.
  .) Un objeto específico de una campaña pueder ser visible o no a los jugadores
  .) Uno general solo puede ser creado por un admin del sistema.
  .) Un DM puede crear específicos para una campaña.

8#CatObjeto

9#Rasgo
  .) puede ser general, o específico de una campaña.
  .) Uno general solo puede ser creado por un admin del sistema.
  .) Un DM puede crear específicos para una campaña.

10#Accion
  .) puede ser general, o específico de una campaña.
  .) Uno general solo puede ser creado por un admin del sistema.
  .) Un DM puede crear específicos para una campaña.

----# Reglas Impostantes de integridad de la BD propuesta por Claude #---
1)Consistencia campaña-personaje: en cualquier endpoint donde se reciban juntos campanaId y personajeId/personajeCampanaId/eventoId, validar que todos pertenezcan al mismo árbol de datos (evitar mezclar entidades de campañas distintas).
2)Transacciones: operaciones que tocan más de una tabla a la vez (ej: crear PersonajeCampana + sus Estadisticas iniciales, o borrar una Campana  deben hacerse dentro de una transacción de Prisma (prisma.$transaction) para evitar estados intermedios inconsistentes.
3)Autorización por fila, no solo por endpoint: no alcanza con "está logueado", hay que verificar en cada operación que el usuario autenticado tiene el rol correcto sobre ESE recurso puntual (dueño del personaje, DM de ESA campaña, etc.), no de cualquier campaña.
4)Validación de existencia antes de vincular: toda FK opcional que el usuario mande (imagenId, eventoId, usuarioId, etc.) debe validarse contra la tabla real antes del create/update, para devolver un 404/400 claro en vez de un error de FK crudo de MySQL.
5)Errores de FK → mensajes de negocio: envolver los try/catch en el service layer para traducir códigos de error de Prisma (P2003 FK violation, P2002 unique violation, P2025 registro no encontrado) a respuestas HTTP con mensajes entendibles para el frontend, en vez de exponer el error crudo de MySQL/Prisma.
6)Borrado lógico vs físico: para Campana, PersonajeCampana y Usuario (entidades con historial importante), evaluá si conviene un borrado lógico (campo activo/estado) en vez de DELETE físico, ya que hoy varias de estas eliminaciones están bloqueadas por RESTRICT precisamente porque tienen historial asociado.
7) "CUU crear un evento con su descripción e imágenes y asignarle personajes": al asignar personajes, validar que pertenezcan a la campaña del evento — y que el usuario que crea el evento sea el DM de esa campaña.
8) Todas las queries por defecto deben excluir registros inactivos, salvo que se pida explícitamente lo contrario.
